A specification that keeps itself up to date

This is a teaching example. It shows a way of writing system documentation in which the documents stay correct as the system changes — not because someone remembers to go back and fix them, but because the structure, and an AI assistant, make it hard for them to drift apart.

The example system is a cash machine: an ATM where a customer can identify themselves with a card and a PIN, withdraw cash, check a balance, transfer money, and print a receipt. Small enough to read in an afternoon, big enough to be realistic.

The problem this addresses

Anyone who has worked on a project of any size knows the pattern. At the start, the documentation is good. Then the product changes. Someone updates the document they were working in. The four other documents that mentioned the same thing are not updated, because nobody realised they mentioned it.

Six months later the documentation says three different things, and people stop trusting it. Once people stop trusting it, they stop reading it, and then they stop updating it. The documentation is now decoration.

This does not happen because people are careless. It happens because the same fact is written down in several places; because one small change touches more documents than anyone expects; and because checking all of them by hand is slow, dull work that nobody has time for. All three are structural problems. Trying harder does not fix them.

The first idea: one connected chain

The documents here are not a folder of separate files. They are a chain, where each document is derived from the one before it.

Domain Model Business Process Use Cases State Charts Epics User Stories Change Log

Read from left to right, each step gets more concrete:

DocumentWhat it answers
Domain modelWhat things exist in this world? A Card, an Account, a Transaction. This is the vocabulary everything else must use.
Business processWhat happens, from start to finish, when a customer walks up to the machine? Every step gets a number.
Use casesWhat is each single goal a customer might have — withdraw cash, check a balance — and how does it play out step by step?
State chartsWhat states can a thing be in, and what moves it between them? A transaction is PENDING, then COMPLETED or FAILED.
Epics & user storiesWhat do we build, in what order, and how will we know it works?
Change logWhat changed in each version, and why?

Two rules hold the chain together.

Everything uses the same words. If the domain model calls it an Account, no other document is allowed to say "bank account" or "the customer's money". This sounds pedantic. It is the whole trick: it means you can search for a word and actually find every place it matters.

Every fact lives in exactly one place. If a diagram already shows the flow, the text next to it does not repeat the flow in words. There is no second copy to forget about. When something changes, there is one place to change it.

How the documents point at each other

The chain is held together by a few shared labels that appear, word for word, in more than one document. The business process numbers its steps: 4a.1, 4a.2, 4a.3. The withdrawal use case then says "corresponds to business process steps 4a.1 – 4a.7", and the story map repeats the same range. So you can pick any user story and follow it back to the exact moment in the customer's journey that it came from — and the other way around, from a step in the process forward to the stories that implement it.

That is what traceability means, and it is the property that makes the whole set worth having. Any single document is just a document. A set where you can always answer why is this here? is a specification.

The second idea: an assistant that does the bookkeeping

A connected chain is good, but keeping it connected by hand is exactly the dull work described above. That is the job given to an AI assistant, which this project calls Jarvis.

You do not tell Jarvis which files to edit. You describe the change the way you would describe it to a colleague. Suppose you say:

"The ATM should also be able to serve a free espresso."

Jarvis then follows a fixed procedure:

  1. It repeats the request back to you, in its own words, so you can catch a misunderstanding before any work is done.
  2. It asks about anything unclear. It is required to ask rather than guess. Is the coffee really free? Does the customer still need to be logged in? What happens when the machine runs out of beans?
  3. It shows you the ripple — a short table: these documents are affected, this is what will happen to each one.
  4. It works through the chain, starting from the vocabulary and moving outward, showing you each proposed change before writing it.
  5. It writes the change down — every touched document, plus a note of what you asked for and what you decided, so the reasoning survives after the conversation is gone.

That one sentence about espresso is not a small change. Coffee is a thing the system did not previously know about, so it needs new vocabulary (a coffee machine, an order). That new vocabulary needs a place in the customer's journey, which needs its own use case, which needs an activity diagram, which introduces an order that can succeed or fail, which needs a state chart, which needs an epic and a user story so somebody can build it — and all of it needs recording. Roughly fifteen files, all of which have to agree with each other.

That is the point. A person given that request would reasonably update three or four documents and miss the rest — not through carelessness, but because holding the whole chain in your head is genuinely hard.

The important part is what stays with the human. Jarvis is not deciding whether the ATM should serve espresso, whether it is free, or what should happen when the beans run out. You decide all of that, and it has to ask you. What it takes over is the part that follows mechanically from your decision: finding everything affected, applying the change consistently, and writing it all down.

Trust, but verify

An assistant that is usually thorough is not good enough to rely on. So the important rules are also checked automatically, by a program rather than by a model. Every time the documentation is built, a script asks questions like:

  • Does every link actually go somewhere?
  • Is every page reachable, or has one been quietly orphaned?
  • Does every diagram file have the name the pages expect? (A mismatch here was silently serving out-of-date diagrams on the published site.)
  • Is every user story listed on the story map, or has one gone missing?
  • When a state chart claims "this happens because of that step over there" — does that step still exist, with that exact wording?

If any check fails, the build stops. Think of it as a spell-checker, except it checks consistency between documents instead of spelling.

This split is deliberate. Anything a computer can check reliably is checked by a computer. The assistant is trusted only with the parts that need judgement.

Why this matters beyond this example

The general idea is not specific to Business Analysis. It is a way of working with any body of knowledge that has to stay true over time:

  • People decide. What should be built, what the trade-offs are, what "correct" means — these stay human.
  • The machine keeps the records straight. Cross-references, consistency, propagating a change to everywhere it lands, keeping a history of decisions.

The same split shows up elsewhere. Andrej Karpathy describes what he calls an LLM wiki: instead of asking an AI the same questions over and over and throwing the answers away, you have it maintain a growing set of linked notes — adding new material, updating cross-references, and periodically checking its own pages for contradictions and stale claims. His summary of the division of labour fits this project exactly: the human's job is to curate sources, direct the analysis and ask good questions; the assistant's job is everything else.

How the pieces fit together

Abstractly, any setup of this kind has four parts and three things that happen to them.

You — choose what goes in, answer the questions, decide what is true

Raw sources

Whatever arrived: a request, a document, a conversation. Kept exactly as it was, never rewritten.

Ingest→

The wiki

Short pages that link to each other. Every fact on exactly one page. Two pages are special:

pagepagepagepageindexlog
Query→

Answers

Assembled from the pages, pointing back at them. An answer worth keeping becomes a page.

↻ Lint re-read the whole thing: contradictions, claims that have gone stale, pages nothing links to, links that point nowhere
The schema — the rules: what kinds of pages exist, what each must contain, how they may link

The four parts play very different roles. Raw sources are the record of what was actually said, so they are never edited — if the wiki and a source disagree, the source wins. The wiki is the only part that grows: it is where understanding accumulates instead of being worked out again from scratch each time. The schema changes rarely, but changing it changes how everything else is written, which is why it is worth being strict about. And you stay at the top: the assistant never decides what is true, only where the consequences land.

The two special pages are what stop the whole thing becoming an unnavigable pile. The index answers "what exists here, and where?" — without it, neither you nor the assistant can tell what might be affected by a change. The log answers "what changed, when, and why?" — without it, every decision has to be re-argued the next time somebody questions it.

The three operations are the only ways anything moves. Ingest brings new material in and folds it into the pages it touches. Query takes knowledge back out, with references, so an answer can be checked. Lint is the one that is easiest to skip and least safe to skip: nothing else notices when two pages have quietly started disagreeing.

The pattern, in Karpathy's own words: A pattern for building personal knowledge bases with LLMs. This project is a worked example of it, applied to a software specification: the documents under docs/ are the wiki, the instructions below are its schema, the change log is its history, and make lint is its health check.

Documentation has always drifted for the same reason: the bookkeeping was too tedious to keep up. That specific obstacle is now much smaller than it used to be, which makes it worth revisiting an old ambition — documentation you can actually trust, because keeping it true is no longer the expensive part.
