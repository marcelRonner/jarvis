# CR-1.0 – Initial Release

The request that started the documentation of the ATM system.

---

## Request

Requested by the owner on 2026-02-22: document the requirements of a new ATM before development
starts. A Customer inserts a Card and enters a PIN, then withdraws cash, checks the Account balance
or transfers funds to another Account, and can take a printed Receipt. The ATM is operated by a Bank,
whose backend holds the Accounts and records every Transaction.

## Analysis

There is no documentation yet, so every artifact is new. The work follows the derivation chain:
the entities and their relationships first, then the end-to-end process that uses them, then the
user goals in that process, then the lifecycle of the entities those goals change, and last the work
breakdown into epics and user stories.

## Decisions

- **Scope** — five user goals: authenticate, withdraw cash, check balance, transfer funds, print a
  receipt. Deposits, PIN changes and ATM maintenance are out of scope.
- **Domain model** — eleven entities: ATM, Bank, Customer, Account, Card, Session, Transaction,
  Receipt, CashDispenser, CashCassette and AuditLog.
- **Actors** — Customer (primary), and ATM System and Bank Backend (supporting), taken from the
  roles in the business process.
- **Authentication** is shared by every other use case, so it is an `<<include>>`; printing a
  receipt is optional, so it is an `<<extend>>`.
- **State charts** — only Transaction has a `status` enum, so it gets the only state chart.
- **Releases** — the story map slices the stories into *R1 – Walking Skeleton*, *R2 – Core
  Transactions* and *R3 – Robustness & Security*.
- **Assumption:** the Bank sets the maximum number of PIN attempts before a Card is blocked, so the
  documentation does not fix a number.
- **Assumption:** the daily withdrawal limit is held per Account by the Bank Backend, not by the ATM.
